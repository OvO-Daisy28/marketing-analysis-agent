# 评测协议

## 假设与对照

H1：受控模板、固定计算与校验能够拦截字段、计算和渲染问题。使用错误注入和浏览器测试验证，不把它包装成模型能力提升。

H2：结构化研究状态相较普通对话历史，改善多轮任务完成和证据追溯。full 与 baseline 共用模型、任务、工具、权限和预算；唯一主要变化是上下文构建。full 注入研究状态并只保留近期完整调用包，baseline 使用普通历史。这是组合机制对照，不能将收益独立归因给某一个组件。

H3：租约、检查点与幂等在中断后避免重复业务写入。通过失效租约、pending 恢复、并发领取与重复发布检验。

## 数据集

development.json 为 30 条开发任务。frozen.json 为 60 个固定场景：20 报表、20 研究、5 修改、10 故障、5 边界。其中 43 个包含真实模型任务，其余 17 个对应确定性工程测试；部分场景共享测试函数，不能把 60 解释为 60 个独立模型样本。

开发任务与正式任务共享任务模板，但改变筛选范围。这适用于工程回归，不能声称跨领域泛化。禁止在正式评测过程中修改 prompt 后只保留更好的结果。

## 评分

- structural_success：状态是否符合预期；研究完成需满足产物与证据结构门禁。
- intent_matched：是否存在符合任务要求的维度和筛选查询；此项不证明最终报告完全满足全部表达要求。
- numerical_checks：用独立 CSV 遍历计算分组分子、分母和比率，与 SQL 聚合结果比较。
- valid_references：结论引用是否存在且属于本目标；不是语义支持率。
- semantic_support：默认 pending_human_review，不能将未复核结果写成准确率。
- 时延包括完整任务流程；失败和超时仍计入报告。P95 采用 nearest rank，样本少时仅作描述。
- Token 包括失败请求保守预留。缺少可信价格时不计算人民币费用。

## 结论审查量表

对每条抽查结论记录：支持 / 部分支持 / 不支持 / 无法判断。检查数值、比较范围、因果用词、样本量和限制是否与引用证据一致。自动模型审查与人类业务审查须分开记录；模型给出引文不意味着审查已经完成。

## 重复与预算

正式任务运行一次。预先选定 research-01、research-02、research-03 和 boundary-1、boundary-2、boundary-3 可额外重复两次；分别报告每次结果，不能把重复样本当成不同任务。

评测器按任务数 × 单任务最大 Token 作保守预算检查，在开始前拒绝超出配置的任务集合。原始结果保存在 artifacts，公开报告只选取已检查不含凭据和私人信息的产物。

## 工程测试命令

pytest 验证权限、CSRF、错误字段、HTML 约束、证据范围、版本、幂等、恢复、重试和预算。Playwright 验证页面生成、iframe 沙箱、实际 G2 canvas、修改和发布。PostgreSQL 专用脚本验证 6 个并发领取者及旧租约隔离。
